## 开发顺序

主线按 `01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 09 → 10`。各阶段边做边补测试和变更记录，不把质量推迟到第 09 阶段。

对原始分组做四个小调整，目录编号仍保持 01～10：

1. **Jest/ESLint 最小工具迁移放在 01**，09 负责全面测试体系；否则 04 的“基础测试”只能继续依赖旧工具，和目标不一致。
2. **配置/日志/trace/版本/健康基础提前到 01、03**，08 负责增强；它们是所有业务验证的前提，不能等业务完成才引入。
3. **User 结构和软删预留在 02**，04 实现行为；避免之后修改唯一性、返回数据及删除约定。
4. **05 的登录失败计数/会话先落 MySQL**，07 再增加 Redis 的共享限流。这样认证不依赖未实现 Redis，又不会临时开放无限登录尝试；不缓存权限以避免撤权窗口。

以下任务已在用户明确授权后完成；验收证据与平台限制详见 [阶段 01 第 8 节](../01-initialization/implementation.md#8-验收标准)。后续阶段仍需按范围授权实施。

4. 添加启动时环境校验，校正 Observe 可选启用与加载顺序，端口非法即启动失败。
5. 按 09 的最小 Jest 配置迁移测试工具，新增 ESLint flat config，保留 Prettier。
6. 统一 `/api/v1`，添加存活接口，启用 shutdown hooks；修正已有 Hello World 测试和实际返回不一致。
7. 执行 typecheck/build/lint/format/test 与 curl 健康检查，记录版本、命令、结果；未通过前不进入数据库迁移。

## 发布前硬性门槛

阶段 04 是隔离开发闭环，不能对外提供无认证用户管理。生产要具备：05 会话撤销和密码安全、06 默认拒绝、07 共享限流及故障策略、08 必需审计与 readiness、09 全部质量门禁、10 备份恢复/Secret/HTTPS。未启用上传等可选功能可不发布，但不能以“以后再做”放行现有接口安全缺口。
