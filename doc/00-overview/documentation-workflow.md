# 文档驱动开发与维护规范

更新：2026-10-23。本规范由 [AGENTS.md](../../AGENTS.md) 引用。

## 工作流程

需求分析 → 检查相关文档/代码/锁文件 → 记录影响 → 更新原实施文档（缺失时新建）→ 用户开发或明确授权代理实现 → 运行验收 → 更新状态/证据 → changelog。重大技术选择先记 ADR。

根 README 和 doc/README 只导航；架构由 architecture 维护；依赖及兼容范围由 tech-stack 维护；数据库完整 Schema 片段分别由阶段 02/05/06/08 所属文档维护；API 共同约定由阶段 03 维护，端点由对应业务阶段维护；其他地方用链接引用。

`doc/README.md` 汇总阶段状态，roadmap 维护顺序与退出门槛，总览说明当前资产，阶段文档维护具体差异和验收证据。状态变化时同步这些摘要，避免重复复制完整契约或另建一套整理方案。既有功能先盘点并原地调整，不照搬旧“新建/初始化”命令生成第二套模块；目录移动与业务/数据库变化分别提交。

## 状态与验收证据

| 状态 | 使用条件 | 记录内容 |
| --- | --- | --- |
| 计划中 | 只有需求/方案/示例 | 前置条件、待确认项 |
| 进行中 | 已开始但验收未完成 | 已做项、剩余项、阻塞 |
| 已实现 | 代码或配置可检查，尚无完整执行证据 | 文件位置、未验收范围 |
| 已验证 | 执行了适用验收且通过 | 日期、版本、命令、结果、证据位置 |

分别维护“文档状态”和“功能状态”：文档写完不等于功能完成。文档自身的链接/结构检查可标已验证，但不能据此标业务功能已验证。总阶段状态取未完成的必需项，不用已完成的一个子步骤覆盖整阶段。

验收记录保留当时日期和代码范围。后续代码变化或测试文件删除后，原测试数量和通过记录仍属历史证据；当前未复验时明确注明，不改写历史，也不把历史通过当作当前代码全部通过。已有代码但缺业务验收的阶段保持“进行中”，仅有角色表不代表 RBAC 已实现。

验收记录至少写：运行目录、系统/Node/依赖版本、配置键名（不写值）、命令、退出码/关键断言、失败项、证据。CI 使用构建链接；本地使用脱敏日志或摘要，不提交真实 token、连接串、个人数据。

## 变更影响检查

| 改动类型 | 必须检查/更新 |
| --- | --- |
| 功能/行为 | 原阶段功能表、步骤、验收和状态 |
| 架构 | architecture、roadmap、必要 ADR |
| 数据库 | 所属阶段 Schema、字段/索引/外键、增量迁移、存量数据与回滚 |
| API | 所属阶段端点、DTO/响应/异常、OpenAPI、调用样例和契约测试 |
| 依赖 | tech-stack 中精确版/engines/peers/用途/原因、锁文件策略 |
| 安全 | 威胁边界、授权模型、错误泄漏、审计和对应测试 |
| 部署 | Docker/Secrets/健康检查/迁移顺序、备份恢复和兼容性 |
| 可复用故障 | troubleshooting 中症状、证据、原因、修复、验证 |

小改动合并入同一个变更记录；重大变更独立一份，用 `YYYY-MM-DD-NNN-topic.md`。变更编号示例 `CHG-20261021-001`。ADR 文件 `000N-topic.md`，保留旧决定及取代关系，不改写历史决策成“从来如此”。

## 命令与示例的约束

- 阶段命令默认工作目录为 `project/`；仓库根目录操作单独标注。文档示例没有在本次执行。
- 标注“后续手动执行”的安装/写库/容器/部署命令必须满足前置条件；文档存在不代表代理获得执行授权。
- 数据库 `migrate dev` 也可能提示 reset：一旦提示，停止，先说明风险、备份与回滚并取得确认。生产只用 `migrate deploy`，不使用 `db push` 代替迁移。
- 新依赖先查正式版与 peers；采用精确版本和单一锁文件。不得通过强制安装绕过不兼容。
- 示例不能包含真实 Secrets，不把 `$TOKEN` 值写进文档。API 调试输入也会产生真实数据，应仅在明确隔离的开发/测试库执行。

## 复核清单

- [ ] 找过已有相关文档，没有另起重复指南。
- [ ] 所有变更有原因、范围、兼容/数据库影响和验证记录。
- [ ] 文档状态和代码状态一致，未运行的验证明确写未执行。
- [ ] 新链接可解析；新增文件名英文；阶段文档保留十个章节。
- [ ] 破坏性动作经过说明和确认，没有泄露敏感信息。
- [ ] 更新导航、路线图的状态和 changelog；历史档案不作为入口。
